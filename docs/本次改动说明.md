# 本次前后端桥接改动说明

## 背景

远程 `main` 已从「管理员 / 员工」点餐版本升级为：

- 商家 `MERCHANT`
- 骑手 `RIDER`
- 顾客 `CUSTOMER`

旧的桥接实现基于 `ADMIN / STAFF` 和堂食桌号，不能直接合并到新版本。本次改动把后端和前端接入层同步到最新三角色外卖流程。

## 主要改动

### 1. 认证契约

- 统一登录入口改为 `POST /auth/login`
- 新增 `GET /auth/me`
- 保留旧登录路径兼容，但新前端只使用 `/auth/**`
- JWT 角色改为 `MERCHANT / RIDER / CUSTOMER`
- `/admin/**`、`/rider/**`、`/user/**` 分别校验对应角色

### 2. 员工模块改为骑手模块

- 删除旧的员工管理接口和前端耦合
- 新增 `/admin/rider/**`
- 支持骑手账号、编号、站点、车型、启停、上线/休息
- 骑手有在途订单时禁止删除
- 停用账号时自动下线

### 3. 新增骑手端后端

- `GET /rider/me`
- `GET /rider/stats`
- `PUT /rider/online`
- `GET /rider/tasks`
- `POST /rider/tasks/{orderId}/grab`
- `GET /rider/orders`
- `POST /rider/orders/{orderId}/finish`

### 4. 外卖订单流程

订单状态保持四段式：

```text
PENDING -> ACCEPTED -> DELIVERING -> DONE
```

- 商家只负责接单或取消
- 骑手抢单后进入配送中
- 骑手确认送达后进入已完成
- 订单保存店铺、收货地址、配送费和骑手快照

### 5. 店铺和收货地址

- 新增 `/user/shops`
- 新增 `/user/shop/{id}`
- 菜单支持 `shopId`
- 新增收货地址增删改查和默认地址接口
- 下单时校验店铺营业状态、起送价和地址归属

### 6. 前端桥接修复

#### Vite 代理

代理前缀从旧的：

```text
/admin /user /upload /api
```

补充为：

```text
/auth /admin /rider /user /upload /api
```

否则新登录和骑手接口会被 Vite 返回 404。

#### 旧会话兼容

浏览器中如果残留旧版 `ADMIN / STAFF` token，新路由守卫会不断把 `/login` 重定向到自身并白屏。现在检测到角色无法映射首页时会主动清理旧会话并停留在登录页。

### 7. 文档

- 更新根 README 的后端状态
- 更新接口契约为三角色与外卖流程
- 新增后端接口兼容清单
- 补充本次改动说明

### 8. 跟进远程最新外卖功能

合并远程后续提交后，又补齐了两部分：

- 骑手的 `todayDone`、`onTheWay`、`doneCount` 和收入全部按真实订单统计，不再依赖骑手表中的缓存值
- 店铺和菜品、套餐增加 `shop_id` 维度；`/user/menu?shopId=` 可返回不同店铺的独立菜单
- 商家后台默认使用 `MERCHANT_SHOP_ID=10001`，不会混入其他店铺菜品
- 当前演示数据包含两家可点单店铺，以及菜单接入中和休息中状态的其他店铺

## 验证结果

已实际验证：

- 商家登录并读取工作台、订单、骑手管理
- 顾客登录并读取店铺、菜单、收货地址
- 顾客用店铺和地址提交外卖订单
- 商家接单
- 骑手抢单
- 骑手确认送达
- 订单最终状态为 `DONE`
- 第二家店铺按 `shopId=10002` 返回独立菜单
- 骑手统计按真实订单计算在途、完成和收入
- 前端 Mock 演示构建通过
- 后端编译和全部测试通过

## 已知边界

- GitHub Pages 演示站继续固定使用 Mock，不会自动连接本地后端
- 真实后端联调需在 `frontend/.env.local` 中关闭 Mock，并设置代理地址
- 生产部署仍需配置正式数据库、JWT 密钥和 Nginx 代理

## 后端接手修复（2026-11-13，桂誉）

在 `backend/platform-compat` 分支上按接口契约逐项补齐，共四组改动：

### 1. 时间格式

`config/JacksonConfig` 统一注册 `LocalDateTime / LocalDate / LocalTime` 序列化器：
`yyyy-MM-dd HH:mm:ss`、`yyyy-MM-dd`、`HH:mm:ss`。此前是 Jackson 3 默认的
`2026-11-13T19:23:43`，与契约不符。

### 2. 计数与分页恢复成数字

根因是 Jackson 把 `Long.TYPE`（基本类型 `long`）也当主键注册成了字符串序列化器。
现在规则固定为：**主键 `Long` → 字符串；计数/分页 `int` → 数字；金额 `BigDecimal` → 数字**。
涉及 `CategoryService`、`OrderService`、`StatisticsService`、`RiderService`。

### 3. 满减

- `shop` 表新增 `full_amount`、`reduce_amount`；`orders` 表新增 `discount`
- 下单按「菜品小计 → 满减 → 打包费 → 配送费」计算：
  `totalAmount = amount - discount + packFee + deliveryFee`，减免额不会超过菜品小计
- 订单出参（下单/详情/列表）新增 `discount`；店铺与菜单出参新增 `fullAmount`、`reduceAmount`
- 种子数据：川味小馆满 30 减 5、稻香快餐满 20 减 3、轻食研究所无、夜宵炸物局满 40 减 8

### 4. 商家端店铺设置接口

- `GET /admin/shop`、`PUT /admin/shop`（详见 `api-contract.md` 3.7 节）
- 店铺固定为配置项 `app.merchant-shop-id`（默认 `10001`），与菜品、套餐的过滤店铺一致
- 校验：满减额不能大于门槛、门槛为 0 不得设优惠额、金额非负、`status/openMenu` 只能 0/1

### 数据库升级提醒

`schema.sql` 使用 `CREATE TABLE IF NOT EXISTS`，**已存在的库不会自动加列**。
老库（如 `diancanyun`）直接启动会报 `Unknown column 'full_amount'`，需要重建库或执行：

```sql
ALTER TABLE shop ADD COLUMN full_amount DECIMAL(10,2) NOT NULL DEFAULT 0,
                 ADD COLUMN reduce_amount DECIMAL(10,2) NOT NULL DEFAULT 0;
ALTER TABLE orders ADD COLUMN discount DECIMAL(10,2) NOT NULL DEFAULT 0;
```

### 测试

- 新增 `BusinessFlowIntegrationTest`：10 个真连 MySQL 的集成用例（登录契约、四向越权、分页数字、
  时间格式、满减命中/未命中、菜单满减配置、商家改配置即时生效、订单全流程）
- 每次运行重建独立测试库 `diancanyun_test`；本机没有 MySQL 时这 10 个自动跳过，不会把构建搞红
- 重写 `ApplicationSmokeTest`：去掉「数据库连不上也算通过」的断言，改为与环境无关的鉴权与结构校验
- `ApiContractRoutesTest` 契约路由表补上 `/admin/shop`
- 当前结果：`mvn test` 23 个用例全部通过

## 第二批：补齐前端新增的券与钱包接口（2026-11-13，桂誉）

`main` 分支的前端在这段时间加了领券中心、团购套餐、骑手天气补贴、钱包与提现，契约里也写清了，
但后端一行都没有，前端全靠 mock，接真后端会 404。这一批按契约原文补齐，改动如下。

### 1. 优惠券（新增模块 `coupon`）

- 新表 `coupon_template`（券模板：面额、门槛、适用店铺、发放总量）与 `user_coupon`（实券：
  归属、状态、有效期、使用时间、抵扣的订单）
- `GET /user/coupon/templates`、`POST /user/coupon/{id}/claim`、`GET /user/coupons`（详见契约 3.8 节）
- 同一种券手上只能有一张未使用的，靠 `user_coupon` 上的生成列 + 唯一索引保证（数据库层面，不只靠代码）
- 过期的未用券在领取前自动置 `EXPIRED`，所以「用掉/过期后能再领」不用手工清数据
- 种子四张券：满 20 减 3、满 40 减 6、川味小馆满 40 减 5（单店）、新客立减 2（无门槛）

### 2. 下单用券

- `POST /user/order` 请求体新增 `couponId`；订单表新增 `coupon_id`、`coupon_title`、`coupon_amount`
- 金额口径更新为：`totalAmount = amount - discount - couponAmount + packFee + deliveryFee`，
  券的抵扣上限是菜品小计，配送费不参与抵扣，总额不会出现负数
- 校验：券属于当前账号、`UNUSED`、未过期、店铺匹配、菜品金额达门槛；核销时 `SELECT ... FOR UPDATE`，
  并发下同一张券只能用一次；下单成功后券置 `USED` 并回填订单号

### 3. 骑手钱包、天气补贴与提现

- 新表 `wallet_record`（提现流水：金额、渠道、状态、时间）
- `GET /rider/weather`、`GET /rider/wallet`、`POST /rider/withdraw`（详见契约 3.8 节）
- 收入口径全局唯一：`完成单数 × 5 + 当日完成单数 × 天气补贴`，`balance = 累计收入 − 已提现`；
  `/rider/stats` 的 `income`、`balance` 与钱包页读同一份计算（原来 stats 用「配送费求和」，与契约不符，已改掉）
- 补贴按时段：夜间 +2、早高峰 +1.5，其余 0；天气本身是演示固定值（没接外部天气源），这一点已登记在契约「已知差异」
- 提现前锁住骑手行再算余额；金额 < 1 → 1001，超过余额 → 4001
- 种子补了一单「今天完成」的订单（5006），让钱包与补贴有可对账的样本

### 4. 菜单返回团购套餐

- `GET /user/menu?shopId=` 出参新增 `combos`：`{id,name,price,originPrice,dishCount,dishNames,image,description}`
- `originPrice` 由所含菜品单价实时累加，`dishNames` 用 `GROUP_CONCAT` 拼好再拆成数组，前端不用二次请求

### 数据库升级提醒（第二批）

```sql
ALTER TABLE orders ADD COLUMN coupon_id BIGINT NULL,
                   ADD COLUMN coupon_title VARCHAR(64) NOT NULL DEFAULT '',
                   ADD COLUMN coupon_amount DECIMAL(10,2) NOT NULL DEFAULT 0;
-- coupon_template / user_coupon / wallet_record 三张新表由 schema.sql 建
```

> `user_coupon` 里有一个 `active_flag` 生成列（`status='UNUSED'` 时为 1，否则 NULL）配合唯一索引，
> 老库手工建表时这两行不能省，否则「同一种券只能有一张未用」的约束就没了。

### 测试（第二批）

- `BusinessFlowIntegrationTest` 从 10 个用例扩到 14 个：领券中心字段类型与重复领取、用券下单与重复核销、
  单店券跨店被拒、菜单 `combos` 结构、钱包公式自洽（`totalIncome = baseIncome + todaySubsidy`、
  `balance = totalIncome − withdrawn`、`stats.income == wallet.totalIncome`）、提现成功与两档非法金额
- `ApiContractRoutesTest` 补 6 条新路由：3 条 `/user/coupon*` 与 3 条 `/rider/wallet|weather|withdraw`
- 当前结果：`mvn test` **27 个用例全部通过**（14 个真连 MySQL）
- 另在临时库 `diancanyun_probe3` 起真服务手工跑了一遍：领券 → 用券下单（38 元单满减 5 + 券 3，实付 35）→
  同一张券再用被拒 → 骑手钱包 10 元提现 3 元后余额 7 元、超额被拒、商家 token 调 `/rider/wallet` 得 403
